# cancho-fetch

An agent-safe `fetch`: HTTP and HTTPS requests to a **fixed, built-in list of hosts**, with that list in the binary's
authority row (`net_out("api.example.com:443")`) where a reviewer can read it, instead of in a flag a caller can set.
Written in [cancho](https://github.com/alpibrusl/cancho), following the contract of
[cancho-tools](https://github.com/alpibrusl/cancho-tools).

**Status: alpha prerelease. Built and tested, not production-ready.** `get`, `head` and `post` over `http` and `https`, redirects to baked hosts only,
per-host credentials read from files, an MCP server, and the authority row derived and gated; CI runs 60-odd loopback tests with
the pinned compiler (cancho 107c0e7, cancho main when it was bumped; the measurements in docs/design.md were made at 597e6b0). The design, what each step measured, and the benchmark against curl are in
[docs/design.md](docs/design.md) (sections 8.1 to 8.7).

**`https` runs on cancho's pure TLS client, which has not had its independent review** (cancho `docs/ROADMAP.md` #281, #209),
and a handshake costs several times OpenSSL's CPU. Do not point it at anything whose confidentiality you cannot afford to lose
to a bug in an unreviewed TLS stack. The trust roots are a PEM bundle embedded at build time (`--roots`); there is no flag that
turns verification off.

Not built yet: wildcard hosts for `https`, several credentials for one host,
and the shared MCP module (the server is a third copy). The landing page (`site/index.html`, generated by `scripts/site_demo.py` from a real session) is published with GitHub Pages once Pages is switched to "GitHub Actions" in the settings.

Building one: `python3 scripts/fetch_build.py --host https://api.example.com --roots roots.pem` (needs the pinned `cancho`
on `PATH`; about three minutes, most of it compiling the TLS packages).

## What it is

```
fetch get  /v1/items --host api.example.com --max-bytes 65536
fetch post /v1/items --host api.example.com --body-stdin --content-type application/json < body.json
```

One binary per allow-list. The hosts are `narrow` literals in the source, so `cancho authority` shows one `net_out` label
per host and nothing else reaches the network: no `ffi`, no `net_in`, no host that is not in the list. A request for any
other host is refused before a socket opens, with a rule tag and the list in `data`.

## Why a separate repository

`cancho-tools` sells "none of these tools can reach the network" as a checked property. A tool that holds `net_out`
would make that "except one", so the network tier lives here with its own ceiling file and its own review, and reuses
the same envelope and contract so a host can treat the two as one family.

## What it depends on

* cancho's exact host matching (`edition 10`, [alpibrusl/cancho#561](https://github.com/alpibrusl/cancho/pull/561)); until it
  is merged the host half of a bound is a prefix and the central claim is not true of the compiler.
* `packages/tls`, `packages/x509` and `packages/http-client` in cancho; the TLS stack's own status is "not independently
  reviewed (#209)", which the design says out loud.

## Not here

`ssh`, other HTTP methods, proxies, cookies, HTTP/2, client certificates. See the design, section 3 and section 8.
